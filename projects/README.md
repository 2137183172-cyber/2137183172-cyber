# 项目导航与能力地图

这份作品集以 AI 工程问题组织：如何管理可信知识，如何约束系统决策，以及如何把自然语言能力接入可控业务流程。

| 主项目 | 用户问题 | 工程核心 | 可复现入口 | 主要边界 |
|---|---|---|---|---|
| [华博士](https://github.com/2137183172-cyber/huaboshi-instrument-agent) | 从实验需求找到有依据的设备建议 | 需求解析、知识检索、流程角色、版本化发布、输出边界 | README 本地启动；合成设备问答；公开 smoke tests | 非真实采购演示；没有发布训练权重 |
| [Lab Repair](https://github.com/2137183172-cyber/lab-repair-agent) | 让用户、工程师和协调方推进一次维修 | 角色档案、规则匹配、竞标、工单与协调状态 | README 本地配置；管理端与小程序构建 | 数据库全流程及真实外部服务未完成公开版联调；LLM 编排待建 |

## 为什么不把每个模块拆成一个仓库

知识发布、场景角色与渠道协作共同服务于一个领域应用；匹配、竞标和工单状态共同构成维修协作基础。保留上下文有助于理解设计约束。模块文档提供源码导航，未来在接口稳定、能独立验证时再考虑拆分。

## 读代码的建议顺序

1. 先看两个项目的 `docs/EVOLUTION.md`：了解什么问题触发了变更。
2. 再看 `docs/MODULES.md`：定位模块输入、输出及边界。
3. 最后看 `docs/ENGINEERING.md` 和 `docs/VALIDATION.md`：理解取舍以及哪些能力仍需验证。

公开版采用独立快照，不导入原项目的商业数据或原始 Git 历史。早期演示仓库 Page1 暂不作为主线作品展示，避免把未经核验的能力写入个人主页。
